## 冒頭の固定文(そのまま貼り付け)

```
【共通の品質基準】
- 本文と背景のコントラスト比はWCAG AA基準(4.5:1以上)を満たすこと。大きい文字(24px以上目安)は3:1以上。
- タップ・クリック可能な要素の実際の反応領域は44×44px以上を目安にすること。
- キーボード操作(Tabキー)だけで全操作が完結すること。フォーカス位置は常に視認できる状態にすること(outlineを消すだけの実装は不可)。
- 色だけに頼って情報を伝えないこと(エラー表示等には色に加えてアイコン・文言も付けること)。

【既定値をそのまま使わない】
- フォントはInter・Roboto・Arial・システム標準フォントを無指定のまま使わないこと。
- 配色にインディゴ〜紫系(#6366F1、#8B5CF6等)を無指定のまま使わないこと。(※本件は下記3.で紫系配色を意図的に指定しているため、この項目の適用外とする)
- 機能紹介等を「均等な3枚カード+アイコン」の定型パターンにしないこと。
- カードの一辺だけに太い色付き境界線を入れる装飾は使わないこと。
- 背景のすりガラス風表現(グラスモーフィズム)は理由なく使わないこと。
- 新しく色・フォント・余白の値を決めた場合は、選んだ理由を一言添えること。

【確認できない項目の扱い】
- hover・focus・アニメーション・レスポンシブの実際の挙動は、静止画やコードだけでは確認できません。実装後、実際のブラウザで動作を確認してから納品してください。
```

## 埋めた10項目

### 1. 対象と利用シーン

このプロジェクトには性質の異なる3つの画面があり、それぞれ想定利用者が違います。

- **スタッフ側(認証+回答フォーム)**: 外注スタッフが、案内されたURLを開き、共通4桁コード→氏名選択→登録メール確認→参加可否・宿泊要否を回答する。基本スマートフォンから、1イベントにつき数回程度のアクセス。
- **確定参加者サイト(公開一覧)**: 決定後の確定リスト(イベント名/会場/開催日/氏名/カテゴリー/最終更新日時)を閲覧するだけの画面。スタッフ・事務局どちらも見る可能性あり。
- **事務局の管理画面**: 事務局が参加決定・公開操作・ホテル室数照合・送信版管理を行う、情報密度の高い業務画面。PC操作が中心と想定。

### 2. 参考イメージ・避けたいイメージ

- **参考イメージ**: ユーザー提供のdribbble音楽アプリ参考画像(IMG_6088.png)。ダーク背景+紫系グラデーション+丸みのあるカード/リスト構成。この雰囲気を3画面すべてに適用する(ユーザー確認済み)。
- **避けたいイメージ**: 明示的な指定なし。ただし8.で述べる通り、事務局の管理画面は情報密度が高い業務画面のため、参考画像のような装飾を強く効かせると可読性が下がるリスクがある(判断が必要な点として下記に記載)。

### 3. 配色

参考画像から実際に画素値をサンプリングして得た値です(目視の推測ではなく、Pythonで座標を指定して読み取った値)。ただし画面拡大率や実機ディスプレイでの見え方までは保証できません。

- **背景**: `#181420`〜`#1A1623`(ほぼ黒に近い、紫がかったネイビー)
- **アクセントカラー(ボタン・アイコン・アクティブ状態)**: `#7C1FC8`〜`#982DF0`(鮮やかな紫)
- **装飾グラデーション帯(バナー・強調カード)**: `#512274`〜`#682791`(深い紫〜赤紫)
- **エラー・成功等の状態色**: 参考画像には含まれていないため未指定。事務局管理画面には却下/送信エラー等の状態表示が必須(確定構成_v1.mdの「事務局決定」「送信エラー」参照)。案件１の評価で「赤系の色が3系統に分かれる」問題が見つかっているため、この新規プロジェクトでは最初にエラー色・成功色をそれぞれ1つずつ変数として決め、以後使い回すこと。

### 4. タイポグラフィ

参考画像からはフォントの実測(書体名の特定)はできません。見出しが太め(ウェイト700程度)の白文字、本文が控えめなグレー、という傾向のみ確認できています。

- **フォント**: 具体的な書体指定なし。OS標準のゴシック系で可(冒頭固定文の「Inter等を無指定で使わない」は西欧圏フォントの既定値回避が主旨のため、日本語UIでは游ゴシック/Noto Sans JP等を明示すること)。
- **サイズ・行間**: 参考画像から実測できないため目安値を使う。本文14px前後・行間1.6、見出し20〜24px。

### 5. 余白の基準

参考画像はモックアップのため実寸が不明で、余白の実測はできません。8pxベース(8/16/24/32px)を基準として指定する。新しい値を追加する場合は理由を明記すること。

### 6. 情報の階層

画面ごとに最優先アクションが異なります。

- スタッフ側: 「回答を送信する」が最優先。
- 確定参加者サイト: 特定の操作はなく、「一覧を素早く確認できること」が最優先。
- 事務局管理画面: 「参加決定/公開操作」および「ホテル室数照合の状況把握」が最優先。

### 7. レイアウトの型

- スタッフ側: 1カラムのフォーム(コード入力→氏名選択→メール確認→回答項目、の縦積みステップ)。
- 確定参加者サイト: リスト/カード一覧(参考画像の「Popular」曲リストに近い、1行1件の情報表示)。
- 事務局管理画面: 表形式のダッシュボード。参考画像はリスト型UIのため、情報密度が高い管理画面にそのまま当てはめると窮屈になる可能性がある(下記「判断が必要な点」参照)。

### 8. 装飾の強弱

ユーザー確認により、3画面すべてに参考画像の装飾(グラデーション・丸みのあるカード)を適用する方針。ただし事務局管理画面は業務画面としての性質上、装飾よりも視認性を優先すべき場面がある(判断層のトレードオフ、下記参照)。

### 9. レスポンシブ対応の範囲

- スタッフ側: モバイル必須(URLをLINE/メールで受け取り、スマホで操作する想定)。
- 確定参加者サイト: モバイル・デスクトップ両対応。
- 事務局管理画面: デスクトップを基準にする(PC操作中心と想定)。ただし外出先での確認需要があるなら、要確認。

### 10. 既存システムとの整合

新規プロジェクトのため、参照すべき既存の共通CSS・デザイントークンはなし。このプロジェクト自体が今後の配色・余白トークンの起点になる。3.で決めた配色・状態色は、GitHub管理のCSS変数として最初に定義し、以後のページ追加時もそこから参照する運用を推奨する。

## 判断が必要な点(私からの指摘。ユーザー判断待ち)

1. **事務局管理画面の情報密度 vs 装飾**: 確定構成_v1.mdによると管理画面は「確保室数」「必要室数」「氏名確定数」「送信後追加/取消/変更」など照合すべき数値が多い業務画面です。参考画像はエンタメ系アプリの装飾密度(グラデーション・大きな余白・少数の情報)を前提にしているため、同じ装飾密度のまま数値の多い一覧・表に適用すると、可読性が下がる可能性があります。管理画面だけ装飾を抑えめにする(背景色・アクセントカラーは踏襲しつつ、カードの大きさや余白は業務画面向けに調整する)選択肢も検討の余地があります。
2. **エラー・成功色の未指定**: 3.に記載の通り、参考画像には状態色の参考がありません。事務局管理画面の「送信エラー」表示等で使う色を、実装前に決めておくことを推奨します。
