# 管理者用デプロイ 再構成案 v1（ドラフト）

作成日: 2026-08-03
根拠: Phase 0 疎通確認（`ping.html`）の実測。管理者用デプロイへの `fetch`（Cookie有無問わず）が
全て失敗し、GitHub Pages + Google ログイン必須 GAS + `fetch` という組み合わせが不成立と判明。

**このファイルはドラフトである。** `CLAUDE.md` §3 への確定事項としての反映は、
オーナーの承認後に別途行う。ここでは案の整理と検討事項のみを記す。

---

## 1. 現状（確定構成 v1 / design-2）からの変化点

| 項目 | 現状 | 第一案（HtmlService）採用時 | バックアップ案（共有管理キー）採用時 |
|---|---|---|---|
| 管理画面の配信元 | GitHub Pages（`design-2/admin.html`） | **GAS `HtmlService` に変更** | GitHub Pages のまま（変化なし） |
| 管理API呼び出し | `fetch`（design-2 実装済み） | **`google.script.run` に書き換え** | `fetch` のまま流用可（変化なし） |
| 管理者認証 | Google ログイン + `ADMIN_EMAILS` 照合（`executeAs=USER_ACCESSING`） | 維持 | **匿名 + 32バイト以上の共有管理キーに後退**（Googleアカウントによる個人識別を失う） |
| 仕様書「GASに画面を置かない」の方針 | 全面適用（確定構成 v1 に明記） | **管理画面に限り例外とする（要：仕様変更承認）** | 維持（画面は置かない方針のまま） |
| スタッフ用の構成 | GitHub Pages + 匿名GAS + `fetch` | 変化なし（Phase 0 で成立確認済み） | 変化なし |
| ADMIN_EMAILS の役割 | 管理者判定の唯一の照合先 | 維持 | **管理者個人の識別ができなくなるため、役割が縮小**（キーは全管理者共通） |

**最大の論点は「仕様書の方針転換を伴うかどうか」。** 第一案は §2-1（絶対に守ること）レベルの話ではないが、
確定構成 v1 の設計方針そのものへの例外を作る。バックアップ案は方針を維持する代わりに、
管理者認証の強度を4桁コードに近い水準まで落とす。

## 2. 修正版プラン（前回レビュー + 追加3点を反映）

追加箇所には **[追加]** を付けている。

### 2-1. 原因（変更なし・確定事項）

```
GitHub Pages → 管理者用GAS → Googleログイン画面へリダイレクト
→ ログイン画面がCORS通信を許可しない → TypeError: Load failed
```

`credentials: 'include'` でも解決しない。GAS 側で
`Access-Control-Allow-Origin: <正確なOrigin>` + `Access-Control-Allow-Credentials: true`
を制御できないため。`Session.getActiveUser()` 自体の不具合ではない（直接アクセスでは成功済み）。

### 2-2. 検証結果（変更なし・確定事項）

| 対象 | 結果 |
|---|---|
| スタッフ用：GitHub Pages → 匿名GAS GET | 成功 |
| スタッフ用：GitHub Pages → 匿名GAS POST | 成功 |
| 管理者用：URLを直接開く | 成功（初回認可あり） |
| 管理者用：`Session.getActiveUser()` | 成功 |
| 管理者用：GitHub Pagesから `fetch` | 失敗 |
| 管理者用：Cookie付き `fetch` | 失敗 |

### 2-3. 第一案：管理画面をGASで配信（`HtmlService`）

```
管理者 → GAS管理画面を直接開く → Googleログイン・認可
→ HtmlServiceで画面表示 → google.script.run → GAS管理処理
```

**構成**: スタッフ画面・スタッフAPIは現状維持。管理画面は `HtmlService`、
管理APIは `google.script.run`、認証は `Session.getActiveUser()` + `ADMIN_EMAILS` 照合。

**必要な追加対応**
- 管理者へ対象スプレッドシートを共有（`executeAs=USER_ACCESSING` は各管理者自身の権限で処理されるため）
- 管理者ごとの初回OAuth認可
- `noreply` 名義が必要な処理（督促メール等）はキューへ積み、オーナー設置トリガーで処理
- 管理操作ログに実行者メールを記録
- 複数管理者で動作確認
- **[追加] 権限が無い状態でのエラーを、生の例外ではなく「アクセス権がありません」に変換する実装**
  （シート共有が外れていると `SpreadsheetApp` 呼び出しが例外を投げるため、これは確認事項であると同時に実装要件でもある）

**技術的な裏付け（2026-08-03 公式ドキュメントで確認）**

- `google.script.run` は Google 公式のHTML Service通信手段。コールバック式（`withSuccessHandler`/`withFailureHandler`）で、
  Promise ネイティブではない
- **[追加] 同時実行数の上限は10件。** 管理画面初期表示で複数のサーバー関数を並行呼び出しする設計の場合、
  項目が増えたときに上限へ接近する可能性がある
- HtmlServiceページは `googleusercontent.com` のサンドボックス化されたiframe内で動作する。
  **[追加] `design-2` の CSS/JS がこのiframe内でそのまま表示されるかは、公式ドキュメントに記載がなく未検証**

**design-2 からの移行コスト（現状把握）**

- `admin.html` の `fetch` 呼び出しをすべて `google.script.run` に書き換える必要がある
  （コールバック式のため、`async/await` のまま流用できない。Promiseラッパーを挟めば書き換え量は減らせる）
- CSS（`tokens.css`・`style.css`）はそのまま使える見込みだが、iframe内での表示崩れは未検証

### 2-4. 第一案の合否確認（開発環境での最小検証）

1. GASから簡単な管理HTMLを配信
2. オーナー以外の第2管理者でログイン
3. メールアドレス許可判定
4. 開発シートの読み取り
5. テストセルへの書き込み
6. 権限を外した後にアクセス拒否されることを確認（**[追加] このときのエラー表示が生の例外文でないことも確認**）
7. PC・スマートフォン双方で確認
8. **[追加] `design-2` の CSS トークンを当てた画面がiframe内で崩れずに表示されるか確認**
9. **[追加] 複数のサーバー関数を同時に呼び出し、10件の同時実行上限に問題なく収まるか確認**

ここまで成功してから本画面を移植する。失敗した場合は移植を途中で進めず、バックアップ案へ切り替える。

### 2-5. バックアップ案：強化した共有管理キー方式（変更なし）

```
GitHub Pages管理画面 → 匿名GAS → 管理者キーをサーバー側で検証 → オーナー権限で管理処理
```

**最低条件**: スタッフ用4桁コードと完全に分離／32バイト以上のランダム管理者キー／
URLに付けずPOST本文で送信／ブラウザ保存は `sessionStorage`／管理操作ログを記録／
認証失敗の試行制限／キーの即時更新・失効手順／可能なら閲覧権限と更新権限を分離。

**個人別の認証・失効はできない。** FGと同じ通信構成であり、GitHub Pagesからの稼働実績がある。

**[追加] design-2 からの移行コスト**: `admin.html` の `fetch` 実装をそのまま流用できる。
第一案（`google.script.run` への書き換え）より移行コストが低い。

### 2-6. 最終的な緊急運用手段（変更なし）

管理画面を公開せず、事務局がスプレッドシートを直接操作する。対象は参加決定・見送り・取消、
公開状態の変更、室数照合、確定リスト確認。恒久構成ではなく、障害時の緊急手順として残す。

### 2-7. 推奨する進行順（変更なし）

```
スタッフ構成は確定
  ↓
開発環境でHtmlService最小検証（8項目に拡張）
  ↓ 成功
Googleアカウント方式で管理画面を構築
  ↓ 失敗
強化した共有管理キー方式へ切替
  ↓ 緊急時
スプレッドシート直接操作
```

## 3. 所感

**技術的な筋は通っている。** レビューの原因分析・検証結果は事前の推測と実測が一致しており、
`google.script.run` の採用は公式ドキュメントでも裏付けが取れた。

**判断の分かれ目は、コストの種類が違う点にある。** 第一案は「実装の書き換えコスト」（`fetch`→`google.script.run`、
iframe内でのCSS検証）を払う代わりに、仕様書が定めたGoogleアカウント認証という
セキュリティモデルを維持できる。バックアップ案は実装コストがほぼゼロ（design-2をそのまま使える）だが、
**管理者個人の識別・失効ができなくなる**という運用上の制約を引き受けることになる。

「開発者不在での運用」が前提のプロジェクトである以上、後から個人の権限を剥奪できない
バックアップ案は、事務局の入れ替わりが起きたときに詰まりやすい。**第一案を基本線とし、
§2-4の最小検証で本当に詰まった場合にのみバックアップ案へ切り替える、という提示された進行順は妥当。**

**未解決なのは技術面よりも仕様面。** 「GASに画面を置かない」という確定事項への例外を
管理画面だけに認めるかどうかは、私からは決められない。ここの承認が、この案を進める前提になる。
