## A-2. 本人確認 **[案]**

design-2 では A-3 のステップに内包しているが、仕様書は
「氏名を選択 → 登録メールアドレスを入力 → 一致したら回答可能」と定めている。

| 区分 | 項目 |
|---|---|
| 表示 | 氏名の候補（在籍中のスタッフのみ）、同姓同名対策としてカテゴリーを併記 |
| 編集 | **氏名**（絞り込み選択）、**メールアドレス**（入力） |
| サーバー | 氏名 + メールの一致判定、スタッフID の払い出し、端末トークン発行 |
| シート | 「スタッフ」（ID・氏名・カナ・会社・カテゴリー・メール・在籍状態） |

**[決定 2026-08-03] 4桁コード未通過の状態では、氏名の候補を一切返さない。**
画面には「未認証です」と表示して止める。

**[決定 2026-08-03] コード通過後も、氏名の一覧を最初から全件表示しない。**
2文字以上入力して初めて候補を絞り込んで返す方式にする。

**理由**: 4桁コードは年度共通で全スタッフに配るため、現実的には漏れる前提で考える必要がある。
コードだけで名簿全件が一覧で抜ける状態を避ける。一方で「氏名を手入力させて完全一致で照合」は、
漢字の異体字・旧姓で一致せずスタッフが回答できなくなる事故を招き、
仕様書が選択式を採った理由（同姓同名の誤選択防止）も失われるため採らない。

# B. 事務局側（GAS HtmlService・Google ログイン）

**全画面の共通要件**: 各サーバー関数の冒頭で `Session.getActiveUser().getEmail()` と
`ADMIN_EMAILS` を**毎回**照合する。画面表示時の1回だけの判定にしない。

## B-2. 回答状況・督促 **[案]**

| 区分 | 項目 |
|---|---|

## B-7. マスタ管理 **[案]**

| 対象 | 表示・編集項目 |
|---|---|
| スタッフ | ID・氏名・カナ・会社・カテゴリー・メール・**在籍状態** |
| イベント | 名称・会場・回答期限・公開状態 |
| 開催日 | 日付・必要人数・予定ホテル |
| ホテル | ホテル名・提出形式・連絡先 |

**[決定 2026-08-03] 当面はスプレッドシートの直接編集に任せ、マスタ管理画面は作らない。**
ただし**将来的には画面化する**。恒久的に作らないという判断ではない。

**理由**: マスタ更新は頻度が低く、仕様書も障害時のシート直接操作を前提としている。
Phase 2〜5 の開発量を優先する。

**画面化するときの注意**: シート直接編集を続けると、列の追加・並べ替えが起きやすい。
**コードから列を位置（列番号）ではなくヘッダー名で参照する**実装にしておくこと。
位置参照だと、事務局が列を挿入した瞬間に壊れる。

## E. 残っている要判断

1. **部屋タイプを事務局側でも扱わないのか。** スタッフの回答項目からは削除が決まったが、
   仕様書の「部屋確保」タブは**ホテル・宿泊日・部屋タイプ別**の確保室数を持つ構造になっている。
   ホテルにはシングル／ツインの区別が実在するため、**事務局が室数を管理する単位として
   部屋タイプを残すのか、それとも部屋タイプという概念自体を廃してホテル×宿泊日の
   室数だけで管理するのか**を決める必要がある。B-5・B-6 の設計に直結する
2. **ホテル提出ファイルの様式**（B-6。着手前に確定が必要）
3. 管理画面を GAS `HtmlService` で配信する第一案の承認（`docs/admin-reconfig_2026-08-03_v1.md`）
